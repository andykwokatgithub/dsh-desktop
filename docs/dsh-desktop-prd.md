## 1. 项目背景与目标

### 1.1 背景
DeepSeek Harness（`dsh`）命令行工具提供 `dsh web` 命令来启动 Web UI 界面（默认地址 `http://127.0.0.1:3080`），但默认会在系统浏览器中打开新标签页。对于高频使用场景，用户更偏好独立的桌面应用窗口，且希望避免误操作导致打开多个重复窗口或浏览器标签页堆积。

> **已核实的实现事实（依据 `@deepseek-ai/dsh` 源码）**
> - `dsh web` 是 `dsh --profile web` 的合法别名；`--no-open` 可用于抑制自动打开浏览器。
> - `dsh web` 启动的是**完整 Harness 运行时**（加载 webserver、API 网关、workspace、前端 dist 等），是一个**长驻服务进程**，而非轻量后台服务。
> - 默认端口 `3080` 可由 web 配置（`cordis.patch.yml` 中 `ctx.webStartup.port ?? 3080`）确认；`--host 0.0.0.0` 被显式拒绝（出于安全），默认绑定 `127.0.0.1`。
> - 浏览器信任栅栏信任 loopback IP 字面量（`127.0.0.1:<port>`），因此 WebView2 以 `http://127.0.0.1:3080` 访问时 `/api` 可正常放行。
> - `dsh web` 支持 `--host <host>` 与 `--port <n>`（`0` 表示由 OS 分配空闲端口），启动就绪后向 stdout 打印 `dsh web: <url>?token=…` 就绪行；该 **token 按进程随机生成，只有 spawn 它的父进程能读到**。
> - 浏览器认证模型为"**进程 token → 签名 cookie**"：`GET /?token=<token>` 返回 303 + `Set-Cookie`；cookie 名绑定 `host:port`，默认有效期 **30 天**，签名密钥持久化在 DSH 凭据中；未携带有效 token/cookie 的索引请求返回 **401**，响应体固定为 `dsh web authentication required; reopen the URL printed by dsh web.`
> - 由上可得两条关键结论：**同一 DSH home 下、同一 `host:port` 的 cookie 可跨 dsh web 进程复用**；但**"非本壳启动"的实例，其进程 token 无法被本壳取得**（既不能直接复用它，也不能为它补发 token）。
> - **进程形态（本机实测，2026-09-11）**：npm 的 `dsh` shim 经 `cmd /c "dsh web …"` 启动后，**真正监听端口的是 `node.exe`**（不是 `cmd.exe`，也不是本壳 `dsh-desktop.exe`）；命令行形如 `"node" "…\npm\node_modules\@deepseek-ai\dsh\lib\bin.js" web --no-open --host 127.0.0.1 --port 3080`，父链为 `node.exe ← cmd.exe ← dsh-desktop.exe`。因此"端口对应哪个进程"可经 `GetExtendedTcpTable`（监听 PID）→ `QueryFullProcessImageNameW`（镜像）/ `Win32_Process.CommandLine`（命令行，同用户进程免提权）直接得到。

本"包装器（Wrapper）"只负责**窗口管理、服务生命周期、单实例防重**，并非复制或替代 Harness 本体。

### 1.2 目标
开发一款基于 **Go + WebView2** 的 Windows 桌面壳程序（Wrapper），实现以下核心能力：

- **无缝嵌入**：通过 WebView2 将 `dsh web` 提供的 Web UI（`http://127.0.0.1:3080`）以原生桌面窗口形式呈现。
- **服务生命周期管理**：自动检测 `dsh web` 后端服务状态，未运行则自动静默启动（带 `--no-open` 参数），等待服务健康后再渲染界面；复用前对既有服务做健康校验，避免复用到陈旧/僵死实例。
- **单例模式（防重复）**：确保系统只有一个应用实例在运行。若用户重复点击启动，自动激活并置顶已有窗口，而非创建新窗口。
- **资源边界声明**：本 Wrapper（Go + WebView2 窗体）资源占用轻量；真正的资源开销来自其托管的 `dsh` Harness Node 进程（详见 §4 非功能性需求）。
- **端口自适应（FR-01）**：不把 `3080` 视为硬约束。首选端口被占用/不可用时，自动改用 **≥10000** 的空闲端口启动本壳自有的 `dsh web` 实例，**绝不打扰**端口上的既有进程。
- **实例归属与认证自愈（FR-04）**：只复用"本壳自己启动且仍健康"的实例；本就属本壳但 cookie 失效时自动停掉并以新 token 重拉；**非本壳**实例则走 FR-05 的 token 附着（或由用户选择改用 ≥10000 端口自有实例）。**关窗停止（`--stop-on-exit`）同样只作用于自有实例，且终止前必须能证明 PID 归属**。
- **快速版本检测与确认式更新（FR-06）**：GUI 启动时后台做"极速"版本检测；发现新版本时在窗口内用 **HTML 页**询问，确认后下载、SHA256 校验、应用并自动重启。
- **可附着的 token（FR-05）**：既支持用 `--url` 把 `dsh web` 打印的带 token URL 交给本壳，也支持在窗口内的 HTML 页里**现场粘贴 token**，据此附着既有实例并完成 token→cookie 交换。
- **HTML 模式窗体（FR-02）**：启动期的一切交互——加载、错误、**token 输入**、**更新询问与更新进度**——一律由 `internal/ui` 内嵌的**本地 HTML 页面**承载，经 `Bind` 桥接与 Go 双向通信，**不再使用原生 MessageBox**（唯一例外：窗口尚未创建时的配置/参数错误）。
- **非本壳 DSH 实例可附着（FR-05）**：若端口上的 DSH 实例不是本壳启动的（拿不到进程 token），或持久化 cookie 已失效，则在窗口内显示 **HTML token 输入页**，让用户粘贴 `dsh web` 打印的认证 URL/token 后**直接使用该实例**；用户也可选择改用本壳自有实例（≥10000 端口）。

## 3. 功能需求详细说明

### FR-01：服务状态检测与自动启动
- **优先级**：P0
- **描述**：应用启动时，用**三层判据**（L1 TCP 监听 PID / L2 dsh HTTP 认证指纹 / L3 进程镜像与命令行）识别端口占用者的身份，再据此决定"复用 / 自建 / 回退端口自建"。
- **逻辑**：
  1. **服务识别（三层判据，收敛后才判"是不是 dsh 实例"）**：
     - **L1 监听探测（TCP）**：用 Win32 `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_LISTENERS)` 判断端口是否处于 LISTENING，并**直接取得监听 PID**。**不解析 `netstat -ano` 文本**：其表头随系统语言本地化、`findstr :3080` 会误配 `:30801` / 对端地址 / IPv6 写法，且多一次子进程开销。
     - **L2 HTTP 指纹**：向 `http://<host>:<port>/` 发 GET（本壳的探测客户端**不带任何 cookie**）。**强证据**：`401` 且响应体为认证栅栏文案前缀 `dsh web authentication required`（并校验 `content-type: text/plain`）；或 `303`（token→cookie 交换）。**弱信号**：`200`——因为探测请求永远不带 cookie，真实 dsh 的索引请求必然被认证边界拦成 401，所以 `200` 只说明"端口上有个 HTTP 服务在 `/` 返回了 200"（nginx / 其它 dev server 亦然），**单独不足以判为 dsh**，必须由 L3 佐证。必要时追加一次 `GET /api/<随机路径>`（dsh 在回环 Host 下返回 `401 unauthorized`）作为第二特征。其它状态码 / 传输错误 ⇒ 该层不命中。
     - **L3 进程身份**：对监听 PID 取**镜像路径**（`QueryFullProcessImageNameW` → `node.exe`）与**命令行**（`NtQueryInformationProcess(ProcessCommandLineInformation)`：类 60 把字符串**复制进调用者缓冲区**（自包含 `UNICODE_STRING`，须先按其返回长度分配），同用户进程**免提权、免 `ReadProcessMemory`、无需 WMI/PowerShell**），匹配 `@deepseek-ai\dsh`（`…\dsh\lib\bin.js`）+ `web` 子命令。
       - **关键字分强弱两档**：`@deepseek-ai\dsh` / `deepseek-harness` / `dsh web` / `…\dsh\lib\bin.js` 为**强证据**；裸 `dsh`、`--port <端口>` 为**弱证据**（本壳自身的 `dsh-desktop.exe --port …` 同样会命中）。**仅凭弱证据不得判为 dsh**，只用于日志与提示。
       - **本机实测样例**：监听 PID = `node.exe`，命令行 = `"node" "…\npm\node_modules\@deepseek-ai\dsh\lib\bin.js" web --no-open --host 127.0.0.1 --port 3080`，父链 = `node.exe ← cmd.exe（cmd /c "dsh web …"） ← dsh-desktop.exe`。
     - **收敛规则**：
       - L2 强证据命中，或 L3 强关键字命中 ⇒ 判为 **dsh 实例**；
       - L2 只有 `200` 弱信号且 L3 不命中 ⇒ **不得**判为 dsh（避免把 nginx / 其它 dev server 当作 dsh 导航过去），按**非 dsh 占用者**处理；
       - **仅 L3 命中**而 HTTP 未就绪（例如前端未挂载时 `/` 返回 404）⇒ 判为**疑似 dsh（启动中）**；
       - **L3 不可用**（他用户进程 / 权限受限 / **端口转发**使监听者不是 node）时降级为 L1+L2，**绝不因"进程信息缺失"改判为非 dsh**；此时若 L2 也没有强证据，则按"证据不足的非 dsh 占用者"处理（保守：不接管、不终止、不导航）并记入日志。
  2. **启动决策**（**不再以"端口冲突"报错退出**）：
     - **自有实例且健康**（记录匹配，见 FR-04）⇒ **复用**：`Navigate` 当前端点，由持久化 cookie 授权；命中认证栅栏则按 FR-04 自愈。
     - **非本壳启动的 dsh**（L2 强证据或 L3 强关键字命中，且不匹配本壳自有实例记录）⇒ **不干扰、不接管**：
       - **端点健康时先按持久化 cookie 尝试附着**（`Navigate` 当前端点）——避免"升级后旧实例没有归属记录"就被误判成必须输 token；
       - 命中**认证栅栏**（即"取不了验证"）⇒ 显示 **FR-05 的 HTML token 输入页**：
         - 用户提交**有效 token** ⇒ `Navigate(http://<host>:<port>/?token=…)` 完成 token→cookie 交换并**附着该实例**（不 spawn）；
         - 用户选择**"改用本壳自有实例"** ⇒ 在本机 **≥10000** 的空闲端口启动自有实例；
         - 用户暂不操作 ⇒ **不 spawn、不终止对方**，停留在 token 页（可随时关闭窗口）；
       - **疑似启动中**（仅 L3 命中、HTTP 未就绪）⇒ 直接显示 token 页（此时 cookie 与 token 都还不可用，页面可重试）。
     - **疑似 dsh（启动中，仅 L3 命中）且匹配自有记录** ⇒ **继续轮询等待**（不重复 spawn、不显示 token 页）。
     - **非 dsh 占用者**（L1 命中，但 L2/L3 均无强证据，含只回 `200` 的服务）⇒ **不干扰该进程**，在本机 **≥10000** 的空闲端口启动自有实例（`dsh web --no-open --host <host> --port <回退端口>`）。
     - **自有实例僵死**（记录匹配，但端口开放而健康校验失败）⇒ 按 FR-04 清理整棵进程树后重新启动。
     - **端口空闲** ⇒ 执行 `dsh web --no-open --host <host> --port <首选端口>` 启动后台服务。
     - **判定先于 spawn**：以上识别必须在任何 spawn（尤其 ≥10000 回退）之前完成，避免对方进程仍在时多起一个 dsh 实例。
     - **回退端口选择**：在 `[10000, 65535]` 内随机取候选，并用本地监听验证其当前可用，再交给 dsh 绑定；若极小概率的绑定竞争导致失败，按启动超时流程报错（见第 4 条）。
     - **日志**：记录最终生效的 `host:port`、选定原因（复用 / 附着 / 首选端口 / 回退端口）以及（可得时）监听 PID 与命令行摘要，便于排查。
  3. **就绪判定**：轮询健康校验（**每 500ms 一次**），整体设置 **冷启动超时 30 秒**；作为补充信号，可同时捕获 `dsh web` 子进程 stdout 中的 `dsh web: <url>` 就绪行。
  4. 若超时仍未就绪，应用显示错误页并退出，提示用户检查 `dsh` 安装或 Node.js 环境（**回退端口同样绑定失败**时走此路径，并在错误页/日志中给出所用端口）。
- **异常处理**：
  - `dsh` 命令不存在：捕获 `exec` 异常，给出友好报错（见 §7）。
  - **Windows spawn 细节**：全局安装的 `dsh` 通常是 `.cmd`/`.ps1` shim（npm 全局 bin）。Go 的 `os/exec` 不会自动按 PATHEXT 解析 `.cmd`，因此**须通过 `cmd /c dsh web --no-open`** 启动，或显式解析出真实脚本路径；同时正确继承 `PATH`、`DSH_HOME` 及用户环境变量（它启动的是完整 Harness，依赖用户配置）。

### FR-02：WebView2 嵌入式窗口渲染
- **优先级**：P0
- **描述**：使用 WebView2 控件创建桌面窗口，加载目标地址。
- **规格**：
  - 窗口标题：`DeepSeek Harness Desktop <version>`（如 `DeepSeek Harness Desktop 0.3.1`），即默认标题模板 `DeepSeek Harness Desktop {version}`，`{version}` 展开为运行时版本（`--title` 不含占位符时按用户给定原样显示，见 README 配置表）。**仅用于显示**；单实例定位不依赖标题，见 FR-03。webview_go 不订阅 WebView2 的 `DocumentTitleChanged`，实测页面 `<title>`（`loading.html` 等）**不会**改写原生标题，故无需在页面加载后 `SetTitle` 复核。
  - 默认尺寸：`1200 x 800` 像素；支持最小化、最大化、关闭等标准系统按钮。
  - **加载态/错误态**：服务未就绪时先加载一个**本地 `loading.html`** 占位页；服务健康后再跳转。冷启动(spawn 的 dsh)时用 `WaitHealthy` 从 `dsh web: <url>` 就绪行解析出的**认证 URL(含启动 token)** 执行 `Navigate`,以完成 token→cookie 交换并加载真实 UI;复用路径直接 `Navigate` 到当前端点（或 FR-05 的 `--url`）,由 WebView2 持久化 cookie 完成授权。**认证栅栏自愈/回退**：页面命中 `dsh web authentication required` 时——**自有实例** ⇒ 自动停掉并以新 token 重新拉起（FR-04）；**非本壳实例** ⇒ 改为显示 FR-05 的 token 输入页，不把用户留在 401 文本页。健康校验持续失败时显示**可重试的错误页**(区分"服务启动中 / 端口或认证失败 / dsh 未安装 / WebView2 未安装")。
  - **导航白名单**：仅允许加载**本壳当前端点**（`http://<host>:<port>`）与 `--url` 显式指定的端点；拦截指向**外部域名、`mailto:`、外部 `http(s)`** 的导航并将其交给系统默认浏览器处理（防止外部页面被信任栅栏 / 脚本上下文错误处理）。
  - **HTML 模式窗体（启动期交互统一，不使用原生 MessageBox）**：`loading.html` / `error.html` / `token.html` / `update.html` / `updating.html` 均为 `internal/ui` 内嵌的**本地页面**，通过 `view.Bind` 双向通信：页面 → Go 走 Bind 函数，Go → 页面走 `view.Dispatch` + `Eval`。
    - 页面契约（JS 全局）：`__dshSubmitToken(pasted)`、`__dshSkipToken()`、`__dshUpdateDecision(update)`；Go → 页面的回调 `__dshTokenResult(ok, message)`、`__dshError(message)`。
    - Bind 回调运行在 UI 线程，**不得阻塞**：耗时的校验/下载一律丢到 goroutine，结果再 `Dispatch` 回页面（页面先用"校验中…/下载中…"占位）。
    - **例外**：窗口创建前的配置/参数错误仍用原生 `messageBox`（此时没有 WebView 可承载）；CLI 命令（`--version`/`--check-update`/`--update`）仍走控制台。
    - 页面只承载本地内容，不放行任何远端资源（与导航白名单一致）。
  - **开发者工具与右键菜单**：默认关闭；提供配置开关（`devtools`、`context_menu`），可在后续迭代暴露。当前版本以"安全默认"为原则。

### FR-03：全局单例与窗口激活（防重复）
- **优先级**：P0
- **描述**：利用 Windows 全局互斥体（Mutex）实现进程互斥，防止多开。
- **详细逻辑**：
  1. 应用启动时尝试创建互斥体（命名：`Local\DSHDesktopApp`）。
     - **命名空间取舍**：默认用 `Local\`（会话内互斥）。`Global\` 会跨会话，可能导致多用户 / RDP 场景下第二个用户无法启动，需在"严格全局唯一"与"多会话可用"之间权衡；本期采用 `Local\`，并记录该取舍。
  2. 若创建失败且错误码为 `ERROR_ALREADY_EXISTS`，判定已有实例运行。
  3. 此时不创建新窗口，而是**激活已有窗口**：
     - 通过**唯一窗口类名**（如 `DSHDesktopAppMainWindow`）用 `FindWindowW(className, NULL)` 定位窗口（**不用窗口标题匹配**，避免标题随页面 `<title>` 变化导致漏匹配 / 误匹配）。
     - 若窗口最小化，调用 `ShowWindow(SW_RESTORE)` 恢复。
     - **激活**：发送自定义注册消息 `RegisterWindowMessage("DSHDesktopApp.Activate")` + `SendMessageTimeout`，让已存在窗口自行置顶；已存在窗口收到后执行 `ShowWindow(SW_RESTORE)` + `SetForegroundWindow`。**前台激活限制**：Windows 限制后台进程直接抢占前台，需叠加 `AllowSetForegroundWindow` / `AttachThreadInput` 等回退，或依靠消息驱动的"窗口自激活"来规避。
  4. 激活完成后，新启动进程立即退出（无痕操作）。

### FR-04：服务生命周期管理
- **优先级**：P0
- **描述**：明确 `dsh web` 后端子进程与 Wrapper 窗口的**归属关系**，以及停止 / 恢复策略。
- **设计决策（默认方案）**：采用"**服务持久化复用**"——关闭 WebView2 窗口时**默认保留** `dsh web` 子进程，后续再次启动 Wrapper 时复用该服务，避免重复冷启动。
  - **复用前健康校验**：每次启动先对当前端点做健康校验（见 FR-01）。若端口开放但健康校验失败 ⇒ 判定为陈旧/僵死服务，**清理整棵进程树后重新启动**（`dsh` 的 Harness 可能派生子 agent / workflow worker 线程，需按进程树一并终止，而非只杀父进程）。
  - **实例归属判定（"是不是自己启动的"）**：本壳在 `%LOCALAPPDATA%\dsh-desktop\web-endpoint.json` 记录自有端点 `{host, port, listenerPid, listenerStartTime, spawnerPid}`——`listenerPid` 是**实际监听该端口者**（实测为 `node.exe`，就绪后用 `GetExtendedTcpTable` 解析），`spawnerPid` 是本壳经 `cmd /c` spawn 的 `cmd.exe`（用于进程树清理）。仅当"**记录存在 + `listenerPid` 仍存活且启动时间一致 + 端点与当前首选端点一致 + 健康校验通过**"四条同时满足时，才按**自有实例**复用（走 WebView2 持久化 cookie 快速进入）；任一不满足即清理记录并重新决策（FR-01 的分支）。同一会话内可用**祖先链**（`node.exe ← cmd.exe ← 本壳 exe`）交叉验证；跨会话时祖先 `dsh-desktop.exe` 已退出，故以记录为准。**复用**判定只看 `listenerPid`（真正在服务端口的就是它）；**关窗停止**的归属判定更宽（包装器也算证），见下方 `--stop-on-exit`。
  - **非本壳实例不接管**：**非本壳启动**的 `dsh`（进程 token 无法取得）不参与复用、也**不被终止**；本壳改为显示 **FR-05 的 token 输入页**（用户可粘贴 token 附着该实例，或选择改用本壳自有实例）。
  - **cookie 失效自愈**：复用自有实例时，若 WebView 命中认证栅栏（持久化 cookie 已失效/过期），本壳按 `spawnerPid` **停止整棵进程树**，并以**新 token 在同类端点重新拉起**。
  - **`--stop-on-exit`（只作用于自有实例）**：关闭窗口时**只**停止**本壳自己启动**的实例（本次 spawn 的，或归属记录证明是本壳启动的，含本壳**上一次**运行启动的实例），并清除端点记录；**非本壳启动的 dsh 实例即使带 `--stop-on-exit` 也不停止**——附着的他人实例（cookie 附着 / token 附着）永不终止。
    - **终止前必须能证明归属**：归属是一条**血脉**而非单个 PID。首选目标是本壳 spawn 的 `cmd.exe` **包装器进程树**（`spawnerPid`）：它随实例终生存在，`taskkill /F /T` 能连带终止当前真正服务端口的进程——即使该进程已换 PID（服务重启/再次派生）、记录里的 `listenerPid` 已过期。记录中的 `listenerPid`（+ `listenerStartedAt`）作为第二目标。证明只认两类："包装器是本壳的**直接子进程**"（本次 spawn），或"包装器 / 监听者仍以记录中的**启动时间**在运行"（跨会话可证；同时要求进程**未退出**，避免进程对象因 handle 未关而在进程死后仍被读作存活）。
    - **不得假装成功**：端口上仍有实例却无法证明归属 ⇒ 返回 `ErrNotOwned`、**放弃终止**并在日志中说明；实例确已退出 ⇒ 记"无需停止"。既不误杀无关进程（PID 复用），也不把"什么都没做"记成"已停止"。
  - **主动停止**：`dsh` 提供"退出"入口（托盘 / 菜单），并提供一个配置项决定"关闭窗口时是否同时停止后端服务"（默认停止服务为**关闭**，即保留），亦可在"退出"时选择"同时停止后台服务"。
  - **版本 / 配置变更防护**：若用户升级 `dsh` 或改动配置，持久化的旧实例可能不匹配；健康校验可加入"进程启动时间戳 / `--version` 差异"作为可选的重新启动信号。
- **可切换方案（备选，写入配置项）**：若希望"窗口关闭即完全退出"，可切换为"Wrapper 拥有子进程，窗口关闭即清理整棵 `dsh` 进程树"。两种方案仅影响资源驻留与二次启动速度，不影响窗口/单实例逻辑。

### FR-05：token 附着既有 DSH 实例（HTML 输入页）
- **优先级**：P0
- **描述**：本壳**取不到验证**时（非本壳启动 ⇒ 拿不到进程 token；或持久化 cookie 失效），**让用户在 HTML 页面上粘贴 token**，从而直接使用该 DSH 实例——而不是另起一个实例，或把用户停在 401 文本页。
- **触发条件**（任一）：
  1. 端点被识别为 **dsh 实例**（L2 强证据或 L3 强关键字命中）且**不匹配本壳自有实例记录**（FR-04）⇒ 非本壳启动、token 无从取得；**且按持久化 cookie 附着失败（命中认证栅栏）**（若 cookie 仍有效则静默附着，不打扰用户）；
  2. `--url` 携带的 token **校验失败**；
  3. 自有实例复用后命中认证栅栏（cookie 失效/过期）⇒ **优先自愈**（FR-04：停掉自有实例并以新 token 重拉），自愈不可用时退回本页。
- **流程**：
  1. 在本壳窗口内显示**内嵌 HTML token 输入页**（`internal/ui/token.html`，非原生对话框），文案说明取值方法：到启动该实例的终端里复制 `dsh web: http://<host>:<port>/?token=…` 整行。
  2. 页面接受**整条 URL 或裸 token**（自动从 `token=` 参数提取）；输入框按密码语义处理，提交后清空。
  3. 提交后本壳先**校验**：`GET http://<host>:<port>/?token=<token>`（不落盘、不入日志）——
     - `303`/`200` ⇒ **有效**：`Navigate(http://<host>:<port>/?token=…)`，由 303 完成 token→cookie 交换并**使用该实例**（**不 spawn**）；
     - `401` / 其它 ⇒ **无效**：页面**内联报错**（"token 无效或已过期，请重新从 `dsh web` 的输出复制"）并保留输入框供重试；**不跳转、不 spawn**。
  4. 页面提供**"改用本壳自有实例"**按钮：按 FR-01 在本机 **≥10000** 的空闲端口自建实例并使用之。
  5. 页面停留期间**不 spawn、不终止对方实例**，窗口保持可用（用户可随时关闭）。
- **`--url` 语义**：`--url` 的 **host/port 从 URL 派生**（未显式指定 `--host`/`--port` 时；显式指定且冲突则报错），URL 必须含显式端口。其 `token` 有效 ⇒ 启动即附着、**不显示** token 页；无效/端点不可达 ⇒ 显示 token 页（便于改正），而不是静默自建。
- **交互实现**：`Bind("__dshSubmitToken", …)` + `Bind("__dshSkipToken", …)`；校验在 goroutine 中进行，结果经 `Dispatch` + `Eval(__dshTokenResult(ok,message))` 回页面（见 FR-02 的 HTML 模式窗体）。
- **安全**：token 只在内存中流转（页面 → Go → 导航 URL），**不落盘、不入日志、错误提示不回显 token**；页面为本地资源，不加载任何远端内容。

### FR-06：启动版本检测与确认式更新
- **优先级**：P1
- **描述**：GUI 启动时在后台做"极速"版本检测；发现新版本时在**窗口内用 HTML 页**询问是否更新，用户确认后下载、校验、应用并自动重启。
- **规格**：
  1. **不阻塞启动**：检测在独立后台协程执行，窗口与界面**不等待**其完成；检测不在启动关键路径上。
  2. **极速**：以"**ETag 条件请求 + 结果缓存**"实现。缓存位于 `%LOCALAPPDATA%\dsh-desktop\update-state.json`，默认 **6 小时**有效；有效期内**零网络请求**直接给结论。单次网络请求预算 **3 秒**，失败**静默**（仅写日志，不打扰用户、不重试）。
  3. **提示（HTML 模式）**：发现新版本且用户**未拒绝过该版本**时，延迟约 **8 秒**（等界面就绪）在窗口内显示**内嵌 HTML 更新询问页**（`internal/ui/update.html`：显示"最新 `<新版本>` / 当前 `<当前版本>`" + "立即更新" / "稍后提醒"两个按钮），经 `Bind("__dshUpdateDecision", …)` 回传选择；**不使用原生 MessageBox**。切页前记住当前界面地址，供稍后返回。
  4. **确认即更新**：选"立即更新"后切到本地"正在下载并安装更新…"页面（`updating.html`）→ 下载 release 资产 → **校验 SHA256** → 原子替换 → **自动重启**为新版本。下载/校验/替换失败 ⇒ 切到**更新失败页**（沿用 error 页样式，说明原因 + "返回界面"按钮经 Bind 让 Go 重新 `Navigate` 回原地址），**旧版本保持可用**。
  5. **拒绝记忆**：选"稍后提醒"即记录被拒绝的版本号，**同一版本不再提示**；出现更新版本时再次提示。
  6. **可关闭**：`--startup-update=false` 关闭 GUI 启动检测。既有 CLI 命令 `--check-update` / `--update` 行为不变（输出到控制台；`--update` 仍不自动重启）。
  7. **安全**：更新包必须通过 release 附带的 **SHA256** 校验；校验不通过即丢弃，不得落地。

## 4. 非功能性需求（NFR）

| 分类 | 要求 |
| :--- | :--- |
| **平台兼容性** | 仅支持 Windows 10 (**Build 17134/1803+**) 及 Windows 11。依赖系统已安装 WebView2 Evergreen 运行时（Windows 11 预装；Windows 10 需手动安装）。 |
| **启动性能** | **热启动**（服务已在运行）：从双击到界面可交互 ≤ **3 秒**。**冷启动**（服务未运行）：窗口与加载态 ≤ 3 秒；服务健康 → WebView 跳转到可交互 ≤ **30 秒**（超时即失败，见 FR-01）。版本检测为**后台任务**，不计入启动路径（FR-06）。 |
| **资源占用** | **仅指 Wrapper 本体**（Go + WebView2 窗体）：内存 < 150MB（闲置），CPU < 1%（闲置）。其托管的 `dsh` Harness Node 进程资源**单列、不纳入此指标**（见 §1.2 资源边界声明）。 |
| **可靠性** | 服务启动超时保护（30s）+ 健康校验重试；首选端口不可用时**自动回退到 ≥10000 端口自建实例**（非本壳 DSH 实例则先走 token 附着页，用户可跳过），且**绝不干扰**端口占用者；更新失败不影响运行中的旧版本；避免因网络栈延迟导致的假性崩溃。 |
| **安全** | 仅允许加载**本壳当前端点**（`http://<host>:<port>`）与 `--url` 显式指定的端点；拦截外部导航；默认禁用开发者工具与右键菜单；`--host 0.0.0.0` 不可用（顶层 dsh 已拒绝）。由于 `/api` 具备执行代码/读写 workspace 的能力，窗口必须依托 dsh 的浏览器信任栅栏，禁止加载任何不被信任的来源。进程 token 与其他凭据**不落盘、不入日志**（FR-05）。进程判据**只读取同用户进程元数据**（监听 PID / 镜像路径 / 命令行：`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`），不注入、不提权，常用路径**不读目标进程内存**；**不 spawn `netstat`/PowerShell**。HTML 模式窗体只承载**本地**页面（不加载任何远端资源）；token 仅在内存中流转（FR-05），输入框提交后清空。 |
| **更新** | 版本检测后台执行、可关闭（`--startup-update=false`）、失败静默；更新**仅由用户确认触发**（不做静默/强制升级）；更新资产强制 SHA256 校验；应用成功后自动重启并复用既有服务（FR-06）。 |

**Node.js 版本说明**：`dsh` 顶层包**未声明自身 `engines`**；`22.19.0+` 来自传递依赖下限（`@earendil-works/pi-ai` 要求 `>=22.19.0`，`commander` 要求 `>=22.12.0`）。实现时应以**实际安装的 `dsh` 所依赖的下限**为准，避免写死一个非官方值。

## 6. 用户操作流程

### 6.1 正常首次启动流程（冷启动）
1. 用户双击 `dsh-desktop.exe`。
2. 程序创建互斥体；创建窗口并显示 `loading.html` 加载态。
3. 程序对 `http://127.0.0.1:3080/` 做健康校验 → 未服务（端口未监听）。
4. 程序执行 `dsh web --no-open`（经 `cmd /c` 解析 shim），轮询健康校验等待就绪。
5. 健康校验返回 HTTP 200 后，WebView2 跳转加载 DSH UI。
6. 用户看到交互界面。

### 6.2 热启动流程（服务已在运行）
1. 用户双击 `dsh-desktop.exe`。
2. 端点记录匹配且健康校验通过（自有实例）→ 复用现有服务，直接跳转加载 DSH UI（快速进入，≤3s）；若记录不匹配（非本壳启动等）则按 §6.4 处理。

### 6.3 重复启动流程（窗口已存在）
1. 用户再次双击 `dsh-desktop.exe`。
2. 程序创建互斥体 → 发现已存在实例。
3. 程序以唯一窗口类定位现有窗口，发送激活消息使其置顶；若最小化则 `ShowWindow(SW_RESTORE)`。
4. 当前双击的进程自动退出，不占用额外内存。

### 6.4 端口被占用时的回退流程（FR-01/FR-04）
1. 用户双击 `dsh-desktop.exe`，但首选端口（默认 3080）已被**其它进程**或**非本壳启动的 dsh** 占用。
2. 程序**不干扰占用者**，在 `[10000, 65535]` 中挑选空闲端口，记录自有端点，并 `dsh web --no-open --host <host> --port <回退端口>` 启动自有实例。
3. 就绪行给出带 token 的认证 URL，WebView2 导航完成 token→cookie 交换并显示界面（日志记录实际端点）。
4. 默认（持久化）策略下，下次启动直接复用该自有端点（健康校验 + cookie）；选择"关闭窗口即停止服务"时，退出即停止该实例并清除端点记录。

### 6.5 启动版本检测与确认更新流程（FR-06）
1. 用户启动应用；后台并行做版本检测（命中 6 小时缓存则**零网络请求**）。
2. 无新版本、已被拒绝过该版本、或检测失败（离线/限流/超时）⇒ **无任何打扰**。
3. 有新版本 ⇒ 约 8 秒后在**窗口内显示 HTML 更新询问页**（"立即更新" / "稍后提醒"）；选"稍后提醒"记录该版本，之后不再提示。
4. 选"立即更新" ⇒ 切到"正在下载并安装更新…"页面 → 下载并校验 SHA256 → 原子替换并**自动重启**为新版本；失败则显示**更新失败页**（含"返回界面"），当前版本继续可用。

### 6.6 非本壳 DSH 实例的 token 附着流程（FR-05）
1. 用户已有一个 DSH 实例在 3080（例如自己在终端里 `dsh web` 启动的）。
2. 用户双击 `dsh-desktop.exe`：程序识别出该端点是**非本壳启动**的 DSH 实例、无法取得进程 token ⇒ 在窗口内显示 **HTML token 输入页**（不弹原生对话框）。
3. 用户回到终端复制 `dsh web: http://127.0.0.1:3080/?token=…` 整行，粘贴进输入框并提交。
4. 程序校验 token：**有效** ⇒ `Navigate` 到该 URL，完成 token→cookie 交换并显示真实 UI（**不新增 dsh 进程**）；**无效** ⇒ 页内报错、可重试。
5. 若用户不想粘贴 token ⇒ 点"**改用本壳自有实例**"，程序在 **≥10000** 端口自建实例并使用（原实例不受影响）。

## 7. 边界情况与异常处理

| 异常场景 | 处理策略 |
| :--- | :--- |
| **`dsh` 未安装 / PATH 未包含** | 捕获 `exec`/`cmd /c` 失败，在**错误页（HTML）**与日志中提示"未找到 dsh 命令，请检查是否已全局安装（npm i -g @deepseek-ai/dsh）"。注意 Windows 下需先正确解析 `.cmd` shim 再判断。 |
| **首选端口被非 dsh 程序占用** | L1 命中、L2/L3 均不命中 ⇒ **不报错退出、不干扰占用者**，改用 `[10000, 65535]` 的空闲端口启动自有实例（FR-01），日志记录实际端点与占用者进程信息（可得时）。 |
| **首选端口上运行着非本壳启动的 dsh** | L2 或 L3 命中且不匹配自有记录 ⇒ 不接管、不终止，另起 ≥10000 端口自有实例（FR-01/FR-04）。 |
| **占用者仅 L3（进程证据）命中，疑似 dsh 启动中** | 匹配自有记录 ⇒ 继续轮询等待，不重复 spawn；否则按"非本壳 dsh"另起 ≥10000 端口实例（FR-01/FR-04）。 |
| **取不到占用者进程信息（他用户进程 / 权限受限 / 端口转发）** | 降级为 L1+L2 判据，**不因缺失进程信息改判为非 dsh**；仍按 L2 结果决策，且绝不终止占用者（FR-01）。 |
| **复用自有实例时 cookie 失效/过期** | WebView 命中 `dsh web authentication required` 栅栏 ⇒ 停掉自有实例并以新 token 在同类端点重新拉起（FR-04）。 |
| **`--url` 的 token 失效 / 端点非 dsh / 不可达** | **不导航该地址**；改为显示 **HTML token 输入页**让用户改正（FR-05），或由用户选择改用 ≥10000 端口自有实例；token 不写入日志或状态文件。 |
| **非本壳 DSH 实例且取不到验证** | 在窗口内显示 **HTML token 输入页**（FR-05）：有效 token ⇒ 附着该实例；选"改用本壳自有实例" ⇒ ≥10000 端口自建；页面停留期间**不 spawn、不终止对方**（FR-01/FR-05）。 |
| **使用（附着）非本壳实例时带 `--stop-on-exit`** | **不停止**该实例（按其归属跳过），日志说明原因；只有自有实例才按"证明"终止（FR-04）。 |
| **自有实例的终止证明不成立**（记录过期、PID 已被复用） | **放弃终止**（宁可不杀也不误杀）并**如实记日志**（端口仍有实例 ⇒ `ErrNotOwned`；实例已退出 ⇒ "无需停止"，绝不记成"已停止"）；端口/记录按陈旧处理（FR-04）。 |
| **用户在 token 页输入无效/过期 token** | 页面内联报错并保留输入框可重试；**不跳转、不 spawn**；token 不回显、不入日志（FR-05）。 |
| **健康但非 dsh 的 HTTP 服务占端口**（只回 `200`、无 dsh 证据） | **不导航**该地址（避免白屏/陌生页面），按非 dsh 占用者处理：≥10000 端口自建自有实例（FR-01）。 |
| **更新提示 / 更新进度 / 更新失败** | 全部由内嵌 HTML 页承载（`update.html` / `updating.html` / 更新失败页），**无原生 MessageBox**；失败页提供"返回界面"（FR-02/FR-06）。 |
| **回退端口绑定竞争失败** | 按启动超时流程显示错误页并清理半启动子进程（FR-01）。 |
| **版本检测离线 / 被限流 / 超时** | 静默失败（仅写日志），不影响启动与使用；命中 6 小时缓存时不做网络请求（FR-06）。 |
| **更新下载 / SHA256 校验 / 替换失败** | 显示**更新失败页（HTML）**并提供"返回界面"，保留旧版本继续可用；校验不通过的产物立即丢弃、不落地（FR-06）。 |
| **`dsh` 服务僵死（端口开放但健康校验失败）** | 按 FR-04 清理整棵进程树后重启服务。 |
| **WebView2 未安装 / Runtime 缺失** | `webview.New` 抛出致命错误，程序捕获并提示下载 WebView2 Evergreen 运行时。 |
| **服务启动超时** | 等待 30s 后显示错误页并退出，日志记录超时错误；不残留半启动的子进程。 |
| **窗口句柄获取失败（唯一窗口类匹配不到）** | 互斥体存在但窗口找不到（进程挂起/僵尸 / 在不同会话桌面），程序记录日志并退出，防止无限循环。 |
| **前端尚未就绪（服务已监听但页面/`/api` 未就绪）** | 通过"健康校验 + 加载态"过渡，先显示加载页，待健康后跳转；避免白屏或 `ERR_CONNECTION_REFUSED`。 |
| **外部链接 / 下载触发** | 外部 `http(s)`/`mailto:` 导航交给系统默认浏览器；文件下载按需由 WebView2 处理或提示。 |

## 8. 验收标准

- [ ] **AC-01**：首次运行（服务未启动），程序自动启动服务、健康校验通过后界面正常显示；期间窗口先显示加载态，无白屏。
- [ ] **AC-02**：连续双击两次 `.exe`，只显示一个窗口；第二个进程自动退出，原有窗口被激活并置顶（即使窗口最小化）。
- [ ] **AC-03**：关闭 WebView2 窗口后，`dsh` 子进程按默认策略保留；重新打开程序时执行**健康校验**（非仅端口探测）后复用该服务；若服务已僵死（端口开放但健康校验失败），程序清理并重启。
- [ ] **AC-04**：窗口标题栏显示 `DeepSeek Harness Desktop <当前版本>`（如 `DeepSeek Harness Desktop 0.3.1`；版本取自 `internal/config.Version`，可由 `-ldflags -X` 覆盖，标题随之一致变化）。
- [ ] **AC-05**：在 `dsh` 未安装/不可解析的环境下运行，程序给出明确错误提示，而非直接崩溃（Windows 下正确处理 `.cmd` shim）。
- [ ] **AC-06**：首选端口被非 dsh 程序占用时，程序**不报错退出、不清杀占用者**，自动改用 ≥10000 端口启动自有实例并正常显示界面，日志记录实际端点。
- [ ] **AC-07**：导航到外部域名时被拦截并交由系统浏览器处理；开发者工具与右键菜单默认不可用。
- [ ] **AC-08**：首选端口上运行着**非本壳启动**的 `dsh web` 时，程序不接管、不终止该实例，另起 ≥10000 端口自有实例；再次启动直接复用该自有实例（不新增 dsh 进程）。
- [ ] **AC-09**：关闭窗口（默认持久化）后重开，健康校验通过即走 cookie 复用（热启动 ≤3s）；`--stop-on-exit` 时退出即停止自有实例并清除端点记录。
- [ ] **AC-10**：`dsh-desktop --url "http://127.0.0.1:<port>/?token=<dsh web 打印值>"` 能直接附着该实例且不 spawn 新实例；URL 的 host/port 自动生效；token 失效时**显示 token 输入页**（而非静默自建）。
- [ ] **AC-11**：存在新版本时应用正常启动（无明显延迟），随后在窗口内显示 **HTML 更新询问页**（非原生对话框）；选"立即更新"经下载 + SHA256 校验 + 替换后**自动重启**为新版本；选"稍后提醒"后同版本不再提示；`--startup-update=false` 或离线时**无打扰、无报错**。
- [ ] **AC-12**：首选端口上是**非本壳** DSH 实例时，窗口显示 **HTML token 输入页**；粘贴 `dsh web` 打印的整条 URL（或裸 token）后完成 token→cookie 交换并**使用该实例**（不新增 dsh 进程）；输入无效 token 时页内报错、可重试且不跳转。
- [ ] **AC-13**：在 token 页选择"改用本壳自有实例"后，在 **≥10000** 端口成功启动自有实例并显示界面；原 DSH 实例**未被终止**。
- [ ] **AC-14**：启动期全部交互（加载 / 错误 / token 输入 / 更新询问 / 更新进度）均由内嵌 **HTML 页面**呈现，界面上不出现原生 MessageBox；唯一例外是窗口创建前的参数错误对话框。
- [ ] **AC-15**：附着到**非本壳** DSH 实例（cookie 或 token 附着）后，即使带 `--stop-on-exit`，关闭窗口也**不会终止**该实例（日志说明"按其归属不予停止"）；只有本壳自建的实例（本次 spawn，或记录中包装器/监听者可证）才会被停止。
- [ ] **AC-16**：`--stop-on-exit` 下，即便记录中的 `listenerPid` 已过期（真正服务端口的进程换了 PID），只要包装器进程树可证属本壳（本壳直接子进程，或仍以记录中的启动时间在运行），关窗即**真的停止**该实例（端口释放、日志列出被终止的 PID），**不会**出现"日志说已停止、实例仍在跑"；若端口上仍有实例却无法证明归属，则**放弃终止并如实记录**，绝不误杀。

## 11. 成功度量建议
- **热启动时间**：双击 → 界面可交互 ≤ 3s（测量口径：进程启动 + 健康校验 + WebView NavigationCompleted）。
- **冷启动时间**：窗口出现 ≤ 3s；服务就绪 → 可交互 ≤ 30s。
- **激活成功率**：重复启动时对既有窗口的激活/置顶成功比例（含最小化恢复）。
- **端口回退成功率**：首选端口不可用时，在 ≥10000 端口成功拉起自有实例并进入界面的比例（目标 100%）。
- **token 附着成功率**：非本壳 DSH 实例场景下，粘贴 token（含无效后重试）最终成功进入界面的比例。
- **更新提示转化**：弹出更新提示后被确认执行的比例、以及更新后自动重启成功率。
- **异常退出率**：因健康校验失败、端口不可用、子进程残留等导致的异常退出比例。
